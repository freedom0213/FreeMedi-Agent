# S1 患者登录、隔离与预约验收

2026-11-18 在独立的 MySQL 8.0.34、Spring Boot 和 Vite 进程上完成验收。S1 通过现有入口的身份隔离与预约正确性基线。Agent 消息和确认的完整重试、故障后的核验恢复仍按 S5 验收。

## 登录与接口

同源的患者页面使用 Spring Security 服务端会话。登录时用 BCrypt 验证密码、检查患者角色及启用状态，并更换会话 ID。浏览器使用 HttpOnly、SameSite=Lax 的会话 Cookie，服务端会话空闲 30 分钟过期。退出使会话和旧 Cookie 失效。任务恢复按患者区分浏览器存储键，同浏览器的其他标签页在登录或退出后重新核对身份。

Flyway 的 V8 数据迁移复用 `sys_user`，仅在原患者仍使用占位密码时更新其密码哈希，并新增第二个合成患者账号。原患者 ID 和预约归属保留。以下密码仅供仓库的本地合成演示。

| 患者 | 账号 | 密码 |
| --- | --- | --- |
| 演示患者 | `demo-patient` | `Mediflow-Demo-A!2026` |
| 演示患者乙 | `demo-patient-b` | `Mediflow-Demo-B!2026` |

| 接口 | 用法 |
| --- | --- |
| `GET /api/v1/auth/csrf` | 获取表单及写请求需要的 `headerName`、`token`。返回当前会话的 `patientId`，匿名时为 null。 |
| `POST /api/v1/auth/login` | 同一 Cookie 会话按 `headerName` 发送令牌，表单编码提交 `username`、`password`。成功 204，凭据错误 401。 |
| `GET /api/v1/auth/session` | 返回当前患者标识和显示名，匿名返回 401。 |
| `POST /api/v1/auth/logout` | 携带当前会话的 CSRF 令牌退出，成功 204。 |

命令行调用方要保存 Cookie，并在登录后重新获取 CSRF 令牌。现有任务、消息及 SSE、确认、预约列表与详情使用会话身份，旧 `X-Demo-User-Id` 请求头不参与授权。匿名读取受保护资源返回 401，缺少有效 CSRF 的写请求可能在认证前返回 403。他人的任务和方案操作返回 403，预约详情返回 404。首页所用的目录和可用号源查询继续公开。

## 本地复验

S2 增加候选选择步骤。按当前版本复验 Agent 预约时，先比较并选择号源，再刷新和确认。见[S2 记录](s2-appointment-options.md)。

1. 启动专用 MySQL 和启用 `mysql` profile 的后端，Flyway 会应用 V8。在已有演示库没有近期号源时，先对该库执行 `scripts/seed-demo-slots.ps1`。
2. 在 `web` 启动 Vite，从 `http://localhost:5173/booking` 进入登录。用第一位患者完成选号、筛选、确认和回看。进入智能导诊，发送“帮我预约呼吸内科的号”，刷新后核对方案，再点击确认。
3. 另开 Chrome 无痕窗口，以患者乙登录并检查“我的预约”。退出患者甲，再访问其页面，应返回登录页。网络接口负面场景可用 `scripts/test-mysql.ps1 -KeepData` 复跑。
