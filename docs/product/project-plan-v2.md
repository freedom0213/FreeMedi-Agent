## 0. Agent 执行模型

本项目采用受限的工具调用循环，由模型、工具、任务状态和后端规则共同组成：

```text
用户目标
  ↓
模型根据上下文和工具说明选择下一步
  ↓
追问用户，或调用一个业务工具
  ↓
后端校验并执行工具，返回结构化结果
  ↓
模型读取结果，决定继续、调整计划、请求确认或结束
```

概念上的最小循环如下：

```text
while task_not_finished:
    decision = model(messages, available_tools)

    if decision is a question:
        pause_and_wait_for_user()
    elif decision is a tool_call:
        validate_by_backend()
        result = execute_tool()
        messages.append(result)
    else:
        return final_response
```

在 MediFlow 中，用户说“帮我约下周三下午的呼吸内科”后，模型可能发现缺少必要条件，于是先追问；信息足够后选择 `findAvailableSlots`，后端查询模拟号源并返回结构化结果；模型整理候选方案并进入等待确认；用户确认后，后端验证方案版本并调用 `createAppointment`；最后通过 `verifyAppointment` 核验，再返回预约结果。

相关组件的职责如下：

- **RAG** 解决“从资料中找什么内容”，本身不会决定下一步业务动作；
- **SSE** 解决“把过程如何流式传给前端”，本身不是 Agent 能力；
- **LangChain4j** 提供模型接入和工具调用的 Java 封装，本身不会替代业务状态机；
- **状态机和后端规则** 负责限制 Agent 能做什么，防止模型绕过确认、权限和事务。

Agent 的决策范围由工具白名单、任务状态、最大步骤数和后端业务规则共同限制。模型不能直接访问数据库、修改任务状态或执行未经确认的写操作。

## 1. 项目定位

MediFlow Agent 帮助患者完成一次可验证的预约任务：理解自然语言目标、补充缺失条件、查询医生和号源、形成候选方案、在用户明确确认后创建预约，并核验最终结果。

它不是医疗诊断系统，也不是完整医院信息系统。项目重点是展示业务型 Agent 的任务编排能力：

- 多轮信息收集；
- 受限工具选择与调用；
- 基于工具结果调整下一步计划；
- 人工确认和高风险写操作保护；
- 任务状态管理、失败恢复和结果核验；
- 业务权限、并发控制、幂等和审计。

## 2. 首版范围

### 2.1 必须完成的主流程

1. 患者输入自然语言预约需求，例如“帮我约下周三下午的呼吸内科”。
2. Agent 提取已知条件，识别缺失条件并追问。
3. Agent 查询科室、医生、排班和可用号源。
4. 指定医生无号时，按照患者已表达的偏好查询替代方案；不能擅自改变未授权条件。
5. Agent 展示包含医生、日期、时段和科室的候选方案。
6. 用户明确确认具体方案。
7. 后端重新校验身份、方案版本、预约规则和号源。
8. 后端以幂等方式创建预约。
9. 系统重新查询并核验预约结果，再向用户反馈。

### 2.2 首版保留的普通业务能力

- 患者登录和基础角色权限；
- 科室、医生、排班和号源的最小管理能力；
- 患者查看自己的预约记录；
- 管理员查看预约记录和 Agent 运行记录；
- 使用模拟医院数据，不连接真实 HIS、医保、支付或真实号源。

### 2.3 首版暂不实现

- 取消和改期预约；
- 完整医院管理后台；
- 医生工作台；
- 多 Agent 协作；
- 复杂长期记忆；
- 模型、Prompt、工具的在线任意配置；
- 复杂运营分析；
- 真实医院系统对接；
- AI 诊断、处方或个体化用药建议。

取消和改期可以在首版预约闭环稳定后作为第二阶段扩展，但不能阻塞核心 Agent 验收。

## 3. 医疗安全边界

Agent 只负责就诊服务和预约信息收集，不输出诊断结论、处方或用药建议。

症状相关输入采用三层处理：

1. LLM 只将用户描述提取为结构化信息，例如症状标签、持续时间和是否伴随发热。
2. 紧急症状识别由后端固定规则完成，命中后优先提示及时寻求急救或线下医疗帮助。
3. 科室匹配由经过审核的规则表完成，Agent 只负责解释匹配结果并继续预约流程。

RAG 只用于医院服务信息、预约规则和就诊须知，不用于读取实时号源、判断患者权限或执行预约。

## 4. Agent 与后端的职责边界

### 4.1 Agent 可以决定

- 是否需要追问缺失条件；
- 查询工具的合理调用顺序；
- 是否查询其他日期或符合用户偏好的替代医生；
- 是否需要再次查询以验证候选方案；
- 如何将工具结果整理为用户可理解的候选方案。

### 4.2 后端必须强制控制

- 用户身份、角色和数据访问范围；
- 工具参数类型和业务规则；
- 科室、医生、排班和号源的真实状态；
- 任务状态迁移是否合法；
- 写操作是否对应用户明确确认的具体方案；
- 事务、并发控制、幂等和重复请求；
- 执行结果核验和审计记录。

模型输出只能作为下一步建议，不能直接改变任务状态，也不能直接写入预约数据。

## 5. 任务状态

首版采用显式状态机，允许的状态为：

```text
UNDERSTANDING
SEARCHING
NEED_MORE_INFO
PROPOSAL_READY
AWAITING_CONFIRMATION
EXECUTING
VERIFYING
COMPLETED
FAILED
CANCELLED
```

关键约束：

- 只有 `AWAITING_CONFIRMATION` 才能等待预约确认；
- 只有确认方案仍有效时才能进入 `EXECUTING`；
- `EXECUTING` 只能由后端受控服务调用写工具；
- 写入后必须进入 `VERIFYING`，不能直接返回成功；
- 工具失败、模型超时和任务超时都必须有明确终态或受限重试；
- 每次状态迁移写入任务事件，便于恢复和审计。

## 6. 业务工具

### 6.1 只读工具

- `searchDepartments`：查询科室；
- `searchDoctors`：按科室、专长和患者偏好查询医生；
- `queryDoctorSchedule`：查询医生排班；
- `findAvailableSlots`：查询指定条件下的可用号源；
- `queryMyAppointments`：查询当前用户自己的预约；
- `getAppointmentRules`：查询预约规则；
- `verifyAppointment`：核验预约记录及状态。

### 6.2 受控写入能力

- `createAppointment`：创建预约。

`createAppointment` 是后端受控业务能力，不注册为模型可自由调用的工具。模型只能形成带版本的预约方案；用户确认后，由后端确认命令校验方案、身份、号源和幂等键，再调用预约应用服务执行写入。取消和改期在后续阶段再加入。

所有工具使用结构化输入和结构化输出，错误通过明确错误码返回，不把异常堆栈直接交给模型。

## 7. 确认协议

预约确认不是一个孤立的布尔值，而是绑定到具体方案的短期确认凭证。凭证至少包含：

```text
planId
patientId
departmentId
doctorId
slotId
planVersion
expiresAt
idempotencyKey
```

执行前后端必须再次检查：

- 当前用户是否仍是原患者；
- 方案是否过期；
- 方案版本是否仍有效；
- 号源是否仍可用；
- 预约规则是否仍满足；
- 相同幂等键是否已经创建过预约。

如果号源发生变化，任务回到 `SEARCHING` 或 `PROPOSAL_READY`，重新展示方案并请求确认，不能静默替换为其他号源。

## 8. 最小数据模型

```text
sys_user
department
doctor
doctor_schedule
appointment_slot
appointment
agent_session
agent_task
agent_turn
agent_tool_call
agent_plan
agent_state_event
operation_audit_log
```

其中：

- `appointment_slot` 表示具体日期和时间段，避免只用排班总数无法表达具体号源；
- `appointment` 保存患者、号源、状态、幂等键和确认方案；
- `agent_task` 保存目标、当前状态、当前计划和终态摘要；
- `agent_tool_call` 保存工具名称、结构化输入输出、耗时、状态和错误码；
- `agent_state_event` 保存状态迁移原因和关联 turn；
- `operation_audit_log` 保存预约写操作的操作者、确认凭证、执行结果和核验结果。

号源创建必须有唯一约束或事务锁。查询有号不代表创建时仍有号，创建时必须重新校验并原子占用。

## 9. 技术架构

首版采用 Java 模块化单体：

```text
Spring Boot
├── appointment       预约、排班、号源和事务规则
├── agent             Agent 编排、状态机、确认和恢复
├── knowledge         医院服务信息 RAG
└── audit             工具日志和业务审计
```

技术栈版本和取舍记录在[技术栈决策 v1](../architecture/tech-stack-v1.md)。当前基线为：

- Java 17 + Spring Boot 3.4.5 + Spring MVC；
- LangChain4j 0.35.0，调用 DeepSeek OpenAI 兼容接口；
- MySQL 8.4：业务数据、任务状态和审计的持久化事实来源；
- Redis 7.4：任务短租约、限流和可重建缓存，不作为业务状态唯一存储；
- Vue 3.5 + TypeScript + Vite；
- SSE：向前端流式返回 Agent 过程消息；
- 模块化单体：不引入微服务、消息队列和独立向量数据库作为首版前置条件。

显式状态机和业务服务负责流程约束，LangChain4j 不负责替代事务、权限和状态管理。

- 普通查询和预约接口；
- 号源并发控制、幂等和预约核验；
- 最小管理页面或管理接口。

### P1：预约编排 Agent

- 自然语言目标解析；

- 只读工具调用；

- 取消和改期预约。

## 11. 首版验收标准

- 患者不知道科室时，Agent 根据症状提供谨慎的导诊方向；能够理解口语日期。明确要求尽快就诊时可查询最早号源，日期和时段偏好不作为必填表单项；
- 指定时间无号时，主动推荐同科室备选时间并说明变化；患者确认前可继续调整，旧方案失效且新方案需要重新确认；
- 指定医生无号时，Agent 只根据用户已表达的偏好寻找替代方案；
- 用户拒绝确认时，不产生预约记录；
- 确认后号源被占用时，不会静默替换号源；
- 重复提交同一幂等键不会创建重复预约；
- 两个请求竞争最后一个号时最多成功一个；
- 工具失败或超时后，Agent 不会声称预约成功；
- 预约写入后核验失败时，界面明确显示待核验或失败状态；
- 用户无法查询其他患者的预约；
- Agent 的每次工具调用和状态迁移都可追溯；
- 明显紧急症状命中规则时，优先提示及时就医，不继续普通预约流程。

## 12. 简历项目叙事

推荐项目描述：

> 基于 Java Spring Boot 和 LangChain4j 构建面向模拟医院预约场景的受限业务 Agent。系统支持自然语言需求解析、多轮信息补全、医生与号源工具编排、候选方案生成、基于方案版本的人工确认、预约幂等与并发控制，以及执行后的结果核验和审计追踪。RAG 仅用于医院服务规则和就诊须知查询，实时业务数据始终由后端工具提供。

面试重点放在：

- 为什么不能让模型直接创建预约；
- 如何设计确认方案和过期处理；
- 如何防止最后一个号被重复预约；
- Agent 状态机如何暂停和恢复；
- 工具日志与业务审计为什么分开；
- 为什么 RAG 不负责实时号源和预约判断。

## 13. 演示与项目叙事

项目面向 Java 后端 + AI 应用开发岗位，计划在 2 到 4 周内完成可演示版本。

演示页面采用“聊天窗口 + Agent 执行轨迹”：聊天窗口展示用户可见内容，轨迹展示当前状态、工具名称、参数摘要、工具结果摘要和确认节点。敏感数据和内部 Prompt 不直接展示给用户。
