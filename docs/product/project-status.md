# MediFlow Agent 项目现状文档

> **文档用途：** 记录当前已讨论并基本确认的产品定位、功能范围、Agent 行为边界和开发优先级，供后续与 Codex 等编码 Agent 继续讨论和完善。
>
> **当前阶段：** 产品规划阶段，尚未开始正式编码。本文记录的是当前方案，不代表所有技术细节已经最终确定。

## 1. 项目概述

**暂定项目名：** MediFlow Agent

**项目定位：** 面向患者与医院工作人员的智能就诊服务平台。患者可以使用常规挂号功能，也可以与 AI Agent 多轮沟通，由 Agent 收集就诊相关信息、查询科室和医生排班，并在患者明确确认后执行预约等操作。

项目重点不是单纯的聊天机器人，也不是让 AI 独立诊断疾病，而是展示一个能够理解目标、调用业务工具、根据工具结果调整计划，并在关键操作前请求确认的业务型 Agent。

### 1.1 项目目标

- 建立从患者查询、导诊、查看号源到预约成功验证的完整业务闭环。
- 展示 Agent 的意图理解、多轮信息收集、工具调用、任务状态管理、异常处理与结果验证能力。
- 提供可管理的科室、医生、排班、知识库和 AI 能力配置。
- 项目规模控制在个人能够逐步完成、方便演示和面试讲解的范围内。

### 1.2 当前明确的产品选择

- 主要用户：患者、医院工作人员。
- 前端形态：患者端 + 管理端。
- 暂不单独开发医生端；医生资料可以在管理端维护。后续若有明确需要，再考虑增加医生工作台。
- Agent 可以自主查询、规划和调整查询步骤。
- 预约、取消、改期等会改变业务数据的操作，必须在执行前获得患者确认。
- 患者可以选择使用 AI 导诊，也可以跳过 AI，直接使用普通挂号功能。
- 首版以模拟医院业务数据为主，不对接真实医院 HIS、支付或真实医疗服务。

## 2. 用户端功能

### 2.1 AI 智能导诊与预约

患者可以用自然语言描述需求，例如“我最近咳嗽”，或者“帮我预约张医生”。

AI 导诊可以通过多轮对话补充必要信息，例如症状持续时间、是否伴随发热等，然后整理成简明的就诊信息摘要，并依据经过审核的导诊规则和医院科室资料提供科室参考。

主要能力：

- 理解患者的就诊服务意图。
- 缺少必要信息时继续追问。
- 查询科室、医生、排班和可用号源。
- 将查询结果整理成清晰的候选方案。
- 支持用户点击“根据导诊结果预约”等按钮，也支持直接通过对话发起预约。
- 执行预约前展示明确的医生、日期、时段等信息，并请求确认。
- 预约完成后重新查询或核验结果，再向患者反馈。

### 2.2 普通预约挂号

患者不必经过 AI，也可以直接：

- 浏览科室及科室介绍。
- 浏览医生资料、职称和专业介绍。
- 按科室、医生、日期和时段查询排班与号源。
- 创建预约。
- 查看自己的预约记录和预约状态。
- 在符合预约规则的情况下取消或改期。

### 2.3 个人中心

首版可包含：

- 个人资料。
- 我的预约、历史预约及取消记录。
- AI 导诊历史和导诊摘要。

收藏医生、收藏科室等属于可选功能，不是首版必需项。

### 2.4 医院服务信息

提供医院介绍、科室介绍、门诊时间、预约规则、就诊须知等信息。这部分既可通过普通页面查看，也可供 AI 通过受控工具查询；适合纳入后续 RAG 知识库。

## 3. 管理端功能

### 3.1 基础业务管理

- **用户管理：** 账号、角色、启用状态等。
- **科室管理：** 科室名称、介绍、状态等。
- **医生管理：** 医生所属科室、职称、专业介绍、账号关联等。
- **排班管理：** 医生、日期、时段、总号源数和可预约状态。
- **预约管理：** 查询和管理预约记录。
- **症状标签 / 导诊规则：** 维护首版使用的基础标签和经审核的导诊规则。
- **预约规则管理：** 例如提前预约范围、取消期限、每人预约限制等。

用户管理和医生管理不是重复模块：用户表管理登录身份与角色，医生表管理医生的业务资料，并关联对应账号。

### 3.2 AI 能力管理

- 大语言模型配置。
- Embedding 向量模型配置。
- 可选的重排模型配置。
- 提示词模板管理。
- Agent 工具的启用状态、说明和参数约束管理。
- 模型调用记录、错误信息和运行状态。

管理页面不能直接开放任意数据库操作。工具的实现、鉴权、参数校验和业务规则必须由后端代码控制。

### 3.3 RAG 知识库管理

- 知识库创建与维护。
- 原始文档上传和解析状态。
- 文档分片查看。
- 向量化任务和索引状态。
- 检索测试。
- 知识库发布与停用。

RAG 主要用于查询医院服务信息、预约规则、就诊须知等有来源依据的内容。首版可以后置到核心预约闭环完成之后。

### 3.4 运行监控、审计和数据分析

- Agent 任务及工具调用记录。
- 管理操作日志和预约操作审计。
- 模型调用异常及工具执行失败记录。
- 预约量、科室预约分布、号源利用率、取消率等基础指标。
- AI 导诊使用量、工具调用成功率等 Agent 运行指标。

## 4. Agent 的行为与安全边界

### 4.1 Agent 的职责

Agent 不是只生成回答，而是围绕用户目标完成一个有状态的任务：

1. 理解用户目标。
2. 判断还缺少哪些必要信息。
3. 必要时向用户追问。
4. 选择合适的业务工具并调用。
5. 阅读工具返回的真实结果。
6. 根据结果继续查询、调整计划或向用户询问。
7. 形成具体操作方案。
8. 对预约、取消、改期等写操作请求用户确认。
9. 由后端校验并执行操作。
10. 再次核验执行结果，向用户反馈。

例如，用户指定的医生没有号时，Agent 可以根据用户已表达的偏好，查询同科室其他医生或其他日期；如果需要改变用户未授权的条件，应先询问，而不是自行替用户做决定。

### 4.2 自主规划与后端强制控制的分工

**Agent 可以自主决定：**

- 查询工具的调用顺序。
- 是否需要追问缺失信息。
- 是否查询其他日期或符合用户偏好的替代医生。
- 是否需要进一步查询来验证候选方案。
- 根据工具结果调整下一步计划。

**后端必须强制控制：**

- 用户身份、角色与数据访问权限。
- 参数合法性和预约业务规则。
- 号源是否仍然可用。
- 写操作是否对应用户明确确认的具体方案。
- 事务、并发控制、重复请求处理。
- 操作结果核验与审计记录。

不能仅因为模型调用了创建预约工具，就直接信任模型并执行操作。

### 4.3 写操作确认

预约、取消、改期属于需要确认的操作。确认内容必须具体，至少能对应到操作类型和目标记录或号源，以及本次待执行操作。

确认不能只是一个没有上下文的“确定”标记。若用户确认后号源已变化、目标方案发生变化或确认已过期，应重新展示方案并请求确认。

后端还需要防止重复提交，并在实际执行时重新校验号源和业务规则。

### 4.4 医疗安全边界

- 本项目是就诊服务与信息收集助手，不定位为能够独立诊断疾病的医生。
- 不提供诊断结论、处方或个体化用药建议。
- 科室建议应基于经过审核的规则和医院资料，并清楚表达其参考性质。
- 遇到明显紧急症状时，应优先提示及时寻求急救或线下医疗帮助，不应继续普通导诊流程或让用户等待预约。
- 演示数据和医学知识内容需要明确标注其用途与来源，避免将演示功能描述为真实医疗诊断能力。

## 5. 建议的 Agent 任务状态

任务状态由后端工作流管理，模型只提出下一步建议，不能任意篡改任务状态。

可考虑以下状态：

- `UNDERSTANDING`：理解用户目标。
- `SEARCHING`：正在查询信息或调用只读工具。
- `NEED_MORE_INFO`：需要用户补充信息。
- `PROPOSAL_READY`：已形成候选方案。
- `AWAITING_CONFIRMATION`：等待用户确认写操作。
- `EXECUTING`：后端正在执行已确认的操作。
- `VERIFYING`：核验操作结果。
- `COMPLETED`：任务完成。
- `FAILED`：任务失败。
- `CANCELLED`：任务已取消。

后续实现时，需要定义允许的状态迁移、超时处理、重试上限和任务恢复方式。避免 Agent 无限循环；工具失败时应能停止并给出清楚的失败原因。

## 6. 候选业务工具

以下为设计阶段的候选名称，实际名称可在开发时调整。

### 6.1 只读工具

- `searchDepartments`：查询科室。
- `searchDoctors`：查询医生及其业务资料。
- `queryDoctorSchedule`：查询医生排班。
- `findAvailableSlots`：查询可预约号源。
- `queryMyAppointments`：查询当前用户自己的预约。
- `getAppointmentRules`：查询预约规则。
- `getClinicInstructions`：查询就诊须知等医院服务信息。
- `verifyAppointment`：核验预约记录及状态。

### 6.2 写操作工具

- `createAppointment`：创建预约。
- `cancelAppointment`：取消预约。
- `rescheduleAppointment`：改期预约。

写操作工具必须在服务端重新执行身份校验、权限检查、业务规则校验和号源检查，并记录操作审计。工具日志和业务审计日志职责不同，不能互相替代。

## 7. 初步数据模型

首版可从以下核心表开始，具体字段、索引和约束留待后续设计：

| 表 | 用途 |
|---|---|
| `sys_user` | 登录账号、角色、账号状态等 |
| `department` | 科室资料 |
| `doctor` | 医生业务资料，关联用户账号和所属科室 |
| `doctor_schedule` | 医生日期、时段、号源总量和已预约数量等 |
| `appointment` | 患者预约记录、预约编号和状态 |
| `agent_task` | Agent 任务目标、状态、结果摘要等 |
| `agent_tool_log` | 工具调用、执行状态、耗时及错误摘要 |
| `operation_audit_log` | 预约及管理操作的操作者、目标、确认信息和执行结果 |

可在后续按需增加：

- Agent 会话和消息表。
- 独立的号源表 `appointment_slot`。
- 知识库、文档、分片和向量索引元数据表。
- 模型配置、提示词模板和工具配置表。

排班与预约必须处理并发。查询时有号不代表创建时仍有号，创建预约时需要在事务中再次检查并更新号源，避免超额预约。具体采用排班计数还是独立号源记录，应在数据库设计阶段确定。

## 8. 技术方案：尚未最终确定

当前优先考虑 Java 技术路线：

- Java + Spring Boot。
- Spring Security 或项目选定的鉴权方案。
- MySQL。
- LangChain4j，用于接入大模型及工具调用。
- 前端框架待定。

备选路线是 Python + FastAPI + LangGraph。它在显式工作流、暂停等待确认和恢复状态方面可能更直接，但会增加维护另一套技术栈的成本。

**当前倾向：** 优先验证 Java + Spring Boot + LangChain4j 是否能满足工具调用、任务状态管理和人工确认需求，再做最终决定。不要仅为了技术名词堆叠框架。

首版不强制采用微服务、消息队列、Redis 或独立向量数据库。等有明确业务需求后再决定是否引入。

## 9. 开发优先级

### P0：先完成业务闭环

- 登录与基础角色权限。
- 科室、医生和排班管理。
- 普通预约挂号。
- 患者查询自己的预约。
- AI 多轮导诊和必要信息收集。
- Agent 调用只读业务工具查询医生与号源。
- 展示候选方案并在确认后创建预约。
- 预约执行后的结果核验。
- 基础异常处理和权限检查。

### P1：完善管理和 AI 能力

- 取消、改期预约。
- Agent 任务与工具调用日志。
- 操作审计。
- RAG 知识库管理与医院服务信息问答。
- 模型、提示词和工具配置。
- 基础数据分析看板。
- 更完整的任务恢复和失败处理。

### P2：可选增强

- 知识库检索质量评估和版本管理。
- 更复杂的运营分析。
- 医生工作台。
- 候补预约等扩展业务。

## 10. 首版明确不做的内容

- 让 AI 诊断疾病或开具处方、用药方案。
- 对接真实医院 HIS、医保、支付和真实号源系统。
- 多 Agent 协作架构。
- 复杂的长期记忆系统。
- 试图复刻完整医院信息系统。
- 在核心业务闭环完成前，先开发大量与主流程无关的管理页面。

## 11. 关键测试场景

- 指定医生有可预约号源。
- 指定医生没有号源，Agent 能基于用户偏好查询可接受的替代方案。
- 用户未提供必要日期或其他信息，Agent 会追问。
- 用户拒绝确认，系统不执行写操作。
- 用户确认后，号源已被其他请求占用，系统重新查询并要求重新确认。
- 用户重复点击或重复提交预约，系统不会创建意外的重复预约。
- 工具调用失败或超时，Agent 不会谎报成功。
- 用户尝试查询他人的预约，后端会拒绝越权访问。
- 预约写入后核验失败，系统不会直接向用户声称预约成功。
- 遇到明显紧急症状时，系统优先给出及时寻求急救或线下医疗帮助的提示。

## 12. 后续与 Codex 协作建议

本文是当前的项目现状说明，不是要求一次性实现所有功能的完整开发指令。后续可以让 Codex 先评审方案并指出风险，再逐步细化架构、数据库、接口和任务状态机。

建议的推进顺序：

1. 评审本文件，指出范围过大、设计冲突和技术风险；先不要写代码。
2. 确定技术栈与整体架构。
3. 设计核心数据库表、索引、状态和并发约束。
4. 设计预约业务接口与权限规则。
5. 单独设计 Agent 工作流、工具参数、确认机制和异常处理。
6. 先完成普通预约闭环，再接入 Agent。
7. 通过测试场景逐项验收后，再扩展 RAG 和管理能力。

每次开发任务应明确：目标、允许修改的范围、验收标准、需要运行的测试，以及最终汇报的文件清单、关键逻辑和测试结果。不要一次性要求编码 Agent 实现全部模块。
