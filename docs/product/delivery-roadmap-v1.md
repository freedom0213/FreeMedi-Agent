## 1. 首版交付目标与边界

一个面向模拟医院的就诊服务 Agent：患者通过页面操作与自然语言共同表达需求，系统查询真实演示目录和号源、检索相关资料、提供可选择方案，在本人确认后完成预约；需求变化或办理失败时，保留上下文继续处理，预约后可获取关联本次就诊的有来源资料。

### 1.1 四个患者业务页面

| 页面                   | 交付职责                                   | 当前基础与需补内容                                 |
| -------------------- | -------------------------------------- | ----------------------------------------- |
| 首页 `/`               | 医院服务门户，保留科室挂号、智能办理、我的预约入口及合成数据说明       | 已有路由与目录入口，继续复用；不新增通用搜索平台或运营看板             |
| 智能办理 `/guide`        | 需求条件、真实候选、选择、确认和结果构成主要办理流程；对话用于补充要求和解释 | 页面和对话共享可编辑条件；可比较真实候选、选择并确认。完整故障恢复及资料咨询仍待后续阶段     |
| 普通挂号 `/booking`      | 不经过 AI 独立完成严格条件查询、选号、核对与预约             | 已有首版；S1 已补筛选清旧选择、查询中禁提交和过期响应丢弃，已通过浏览器预约验收 |
| 我的预约 `/appointments` | 查看本人预约列表、详情、来源和真实状态，进入关联就诊资料/咨询        | 列表和详情可进入本次预约的只读就诊准备咨询                    |

必要的最小登录页面/入口属于身份支撑，不扩张为完整账号中心。方案和预约必须能通过页面选择、修改、确认和回看，不能全部只以助手文字呈现。

### 1.2 沿用的原则

- 保留单 Agent、模块化单体、受限只读工具循环和共用预约写服务；不为增加技术名词重做架构。
- 模型决定追问、查询和解释，后端掌握身份、参数、状态、确认、事务、幂等与核验；聊天中的“确认”不能代替具体方案确认。
- 已明确科室/医生时可直接办理；只描述不适时提供谨慎的就诊方向参考，不要求无限问诊。对不确定或本院不支持的服务如实说明，不编造科室和医生。
- 推荐依据限于条件匹配和资料记载，不做复杂偏好评分，不把语义相似度说成医生能力排名。
- 需求条件先覆盖科室、医生、日期、时段及必要的“必须/优先”区别，不做长期健康档案或记忆系统。
- 实时号源、目录启用与预约结果由业务系统核实；资料检索不代替库存、权限或强制业务规则。
- 全部使用合成医院数据；不提供诊断、处方或个体化用药，不对接真实医院、医保或支付。普通挂号不推断已安排检查。
- 首版面向本地求职展示；无公网运维和规模化部署目标，但所选能力必须有实际实现、测试及可复现证据。

## 6. 验收标准

### 6.1 验收方式与状态

下表是**待执行的通过条件**，不是通过报告。本轮没有修改代码或重跑测试。S0 记录基线；各阶段补相应证据，S6 做全链路验收。

- 自动化验证权限、确认/版本、库存与幂等、协议、状态、超时/恢复和资料生命周期等可重复约束。
- 用少量真实模型调用及浏览器操作验证自然语言、真实工具选择、流式体验与业务操作；可控测试不能替代真实模型验收，单次真实调用也不能替代稳定回归。
- RAG 固定问题集覆盖支持/同义表达、混淆、无依据、失效资料、实体不一致与资料中的伪指令。记录预期依据、实际候选、引用/回答一致性、错误和耗时，不按向量分数直接认定有依据。
- 每项记录环境、模型/资料/配置版本、实际结果和证据位置。原始敏感内容及密钥不入证据；不展示模型隐藏思考。

### 6.2 可操作的通过条件

| 编号  | 场景/对应范围              | 必须满足的结果                                                                                              |
| --- | -------------------- | ---------------------------------------------------------------------------------------------------- |
| A01 | 直接办理与需求不完整 / F1、F3   | 明确科室/医生可直接查，不强迫重走问诊；只描述不适时适度补问、给可调整方向。未知/本院未开设不伪装成未来无号，不生成诊断结论                                       |
| A02 | 页面/文字共同调整 / F1       | 两种方式更新同一任务与可见条件；保留已知条件，不互相覆盖丢失；不要求患者记住隐藏参数                                                           |
| A03 | 候选与选择 / F2           | 展示不超过 3 个实际查询候选，不足时显示真实数量；解释条件匹配及让步；页面点击选择后确认单与所选记录一致，查询不占库存                                         |
| A04 | 必须条件与优先偏好 / F3       | “必须周六”和“周六优先”产生不同调整行为；无法满足必须条件时明确无精确方案并等待授权，不静默放宽；更换医生/时间说清变化                                        |
| A05 | 咨询与修改 / F3、F6        | 问理由或材料不失效原方案；真正改条件后旧方案不能提交，必须对新方案重新确认                                                                |
| A06 | 普通挂号与写时有效性 / F4      | 严格查询不静默换条件；选中后修改筛选不能带旧选择提交。直接构造过时、关闭或目录停用号源也被后端拒绝，确认内容与实际写入一致                                        |
| A07 | 确认与方案版本 / F4         | 未确认不写预约；聊天“好的”不执行；过期、旧版本、非本人方案被拒绝，不静默替换目标                                                            |
| A08 | 重复与并发 / F4、F7        | 同号源竞争最多一笔成功；失败方保留需求、重新查候选并由用户重新选择/确认，不能自动换号提交。同意图的网络重试不重复预约；同键换目标报冲突。分别验证消息重试和确认重试，不能仅凭写服务唯一键宣称入口已幂等 |
| A09 | 暂时查询/模型故障 / F7       | 输入和已知需求保留，可明确重试；工具与模型执行有真实限时/有限步骤，不无限循环；资料故障不会无端结束原预约办理或重复写入                                         |
| A10 | 刷新和中断 / F1、F2、F7     | 恢复已保存的条件、候选/所选方案和最终事实；网络暂时错误不清除有效 taskId。处理中状态有明确查询/恢复出口，不凭空宣称成功，不要求完整自动接管平台                         |
| A11 | 提交结果不确定或核验失败 / F4、F7 | 写入可能已成功时先按原意图/预约查询核验；只核验或返回原结果，不重建一笔；已提交预约不会因核验失败被描述为确定未创建                                           |
| A12 | 有依据回答与医生资料 / F5      | 引用来自实际返回且仍发布的同版本片段，可展开标题/章节/原文/来源；医生与科室启用及归属核对，不移植他人专长，不把相似度当能力排名                                    |
| A13 | 无依据、故障与恶意资料 / F5     | 无资料依据不编造；索引不可用明确“暂时查不到”，与无依据区别；不执行资料中的伪指令，不能仅凭候选数量或分数生成答案                                            |
| A14 | 预约后服务 / F6           | 从本人预约详情进入关联就诊的资料/只读咨询，保留科室/医生/时间事实并可返回预约；不能再次执行原预约，普通预约不推断已安排检查或禁食停药                                 |
| A15 | 真实身份与隔离 / E1         | 至少两个预置患者实际登录/退出；未登录、其他账号、伪造用户 ID 无法读/改受保护任务、方案、预约和咨询；REST/SSE/恢复入口均使用服务端身份                           |
| A16 | 资料生命周期 / E2          | 同内容导入不重复，更新升版本，已下架不会因重复导入复活；下架/旧版不再回答引用，索引丢失可重建，失败可查看/重试；不靠删文件或临时改库下架                                |
| A17 | 追踪与结果一致 / E3         | 能沿 taskId 找到轮次、动作、工具参数/结果摘要、耗时和原因；流式展示、保存回复与最终业务事实一致，不出现流式说成功但实际失败                                   |
| A18 | 本地复现与最终材料 / E4、E5    | 干净的专用开发环境按文档启动、生成近期号源、导入/重建知识并执行场景；证据报告已执行/失败/跳过和未测项，无密钥、虚构性能或临床效果                                   |

上述用户操作须通过页面完成选择、修改、核对、确认和查看凭证；不能全部用自由文本指令或手动改数据库代替。复杂口语不承诺全覆盖，支持范围与未覆盖项必须在评估中明确。

## 7. 分阶段开发顺序

每阶段交付必须同时说明：改了什么、为何修改、实际效果、验证证据、潜在影响和遗留；实现与文档同步。不可因接口存在、页面有按钮、离线假模型通过、历史测试数很多或演示某一次成功就标整阶段完成。
