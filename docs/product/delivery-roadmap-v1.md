# FreeMedi-Agent 整体交付计划 v1

> 更新：2026-10-15。面向 Java 后端 + AI 应用开发岗位的核心简历项目。
> 本文是整体范围、顺序和完成标准的统一入口；旧计划用于追溯讨论，不能作为已实现能力证明。
> 状态：Agent + RAG 的目标已获用户认可；下面是推荐交付基线，阶段细节随验证结果调整，不随每次会话临时扩张。

## 1. 最终交付什么

一个患者可以实际走完的模拟医院就诊服务系统：描述不适或直接选择科室，得到可解释的就诊方向，查询医生和实时号源，在本人确认后完成预约，查看预约结果，并查询相关就诊准备资料。管理员能维护演示业务数据、发布知识资料、查看 Agent 调用记录。

Agent 是主线，RAG 是必须完成的业务能力，Java 业务系统保证预约正确性。系统使用合成医院、医生、患者和号源，不连接真实医院；不提供诊断、处方或个体化用药。不得把导诊建议称为医学诊断。

**典型完整演示：**患者描述反复胃部不适 → 可选择继续补充或立即分诊 → 展示暂定科室和理由 → 从本院目录查医生及专长 → 查合适号源，无号时解释替代时间 → 患者确认后创建并核验预约 → 患者询问就诊准备，Agent 检索已发布的医院资料并引用来源。

检查准备必须对应具体检查及医院资料；普通门诊预约不能自动推断已安排胃镜等检查，也不能擅自要求禁食或停药。

## 3. 业务和技术边界

| 信息或动作 | 事实来源/负责模块 | 原因 |
|---|---|---|
| 患者不适、就诊偏好 | 对话上下文 + 患者补充 | 缺失信息不能由模型编造；允许不知道、跳过非必要问题 |
| 暂定科室方向和解释 | Agent 综合现有信息；后端校验目录 | 区分建议、医院未开设和实际无号 |
| 医生身份、所属科室、启用状态 | MySQL 目录工具 | 必须能映射到本院真实演示记录 |
| 医生详细专长、服务范围说明 | 已发布资料 RAG + MySQL 身份校验 | 语义匹配有用，向量相似度不代表医疗能力排名 |
| 排班、号源、预约状态 | MySQL 实时查询 | 不从向量库读取实时库存 |
| 就诊须知、预约政策、检查准备 | 已发布医院资料 RAG | 提供来源、版本及适用范围 |
| 强制预约约束、权限、确认、写入 | 后端代码/业务配置 + MySQL | 文档和模型不能覆盖业务规则 |
| 最终预约结果 | 确认命令 + 写后查询核验 | 聊天说“好的”不直接创建预约 |

安全实现应如实分层：当前主要依赖模型提示词，并未完成经医学审核的分诊规则系统。后续增加少量明确急症信号的代码保护和负面测试，但不宣称能排除所有急症；含糊、否定、历史症状要避免机械关键词误判。

## 4. 患者使用路径与异常路径

| 场景 | 应有行为 |
|---|---|
| 只说“头疼” | 先问少量关键问题，随时允许发起初步分诊 |
| “不知道、我说不清、先帮我挂号” | 解释不确定性，给暂定方向/全科入口；不无限重复问诊 |
| 已明确科室/医生 | 直接查目录和号源，保留必要急症提示，不强制重走症状采集 |
| 急症信号 | 优先显示急诊/急救建议，不把普通预约包装成及时处置 |
| 建议科室本院没有 | 明确“本院未开设”，不能说“未来90天都没号”；不自动替换临床方向 |
| 科室存在但指定时间无号 | 显示替代日期/时段及改变原因，等待选择 |
| 指定医生无号 | 可建议同科室其他医生，但说明更换并让用户选择 |
| 推荐不合适 | 允许继续补充和修正；旧待确认方案失效，新方案重新确认 |
| 没有知识依据 | 说明资料不足，不伪造引用、准备要求或检查安排 |
| 模型繁忙/流式中断 | 保留患者内容，标明未完成；恢复服务器已保存结果后再决定重试 |
| 无号源/咨询结束 | 明确下一步，并允许继续咨询或调整需求，避免无号即锁死聊天 |
| 确认时号源被占/过期 | 不显示成功，不静默替换；重新查询后再确认 |

## 5. RAG 的现实用途与设计

### 5.1 首批知识范围

1. 医院服务指南：挂号、就诊地点、签到、迟到、预约及取消政策。
2. 科室服务范围：本院科室接诊方向、容易混淆的服务边界。
3. 合成医生详细介绍：专长、出诊服务范围；关联稳定的 doctorId/departmentId。
4. 检查准备说明：有明确资料依据时回答相应检查问题，展示适用人群和例外提示。

演示医院政策与医生资料明确标为合成资料。医学相关说明优先使用可核查的医院/机构公开资料并保存出处、日期和适用范围，发布前人工核对；不同医院的具体要求不能直接说成演示医院现行规定。开发阶段先使用 Markdown/纯文本，不为支持复杂扫描 PDF 增加 OCR。

### 5.2 推荐技术方案及替代方案

| 方案 | 优点 | 局限/适用场景 |
|---|---|---|
| MySQL 关键词/专长字段查询 | 简单、目录匹配准确 | 适合短字段；长资料与不同说法匹配有限 |
| 向量检索 + metadata 过滤 | 适合症状描述与服务资料语义匹配 | 存在相近但不适用的召回，必须验证来源和实体 |
| 向量 + 关键词融合 + rerank | 可改善精确术语和语义排序 | 增加调优成本，应由评估证明收益再加入 |

推荐以 **LangChain4j + Qdrant + 中文 Embedding** 完成第一版语义检索，保留 MySQL 目录精确查询。沿用技术栈文档的 Qdrant 1.13.x、BGE-M3/SiliconFlow 候选基线；实际镜像补丁、模型可用性、维度和凭证需接入时验证，不能把 DeepSeek 对话 Key 当作 Embedding Key。Rerank 和融合检索列为质量优化项，不能无测量直接宣称必要。

### 5.3 入库和查询闭环

```text
导入资料 → 草稿 → 核对并发布 → 按标题/段落切块 → Embedding → Qdrant
患者问题 → Agent 选择 searchHospitalKnowledge → 类型/科室/发布版本过滤
        → 返回命中片段与来源 → 模型解释并引用 → 页面可展开原文片段
医生推荐 → 对命中 doctorId 查 MySQL → 核实启用、科室和号源 → 展示候选
```

MySQL 保存文档元信息、版本、发布/索引状态和片段原文；Qdrant 是可重建的索引。每个片段保存 documentId、version、chunkId、标题、类型、科室/医生 ID、来源、发布时间。更新/下架后不能继续返回旧版本；索引失败要可重试，重新入库不生成重复片段。模型不能从检索片段获得执行指令，引用内容作为资料而非系统命令。

首版使用标题/段落切块、适量重叠，具体块长和 TopK 通过小规模对照确定；检索分数不能跨模型套用通用阈值。必须支持无证据回答、来源定位、文档失效及实体不一致处理。

## 6. 分阶段交付顺序

工时是从当前代码起算的单人专注开发估计，不是承诺日期；不包括等待用户反馈、外部服务故障和资料核对。约 16—23 个工作日，可并入原先 2—4 周目标的上沿；时间不足先减少管理端编辑面和可选优化，不能删掉引用、确认门禁和关键测试来假装完成。

| 阶段 | 内容 | 完成标准 | 预计 |
|---|---|---|---|
| M1 患者对话体验收敛 | 真流式、推荐卡片、立即分诊、失败消息保留、无号可继续、目录校验 | 首条回复增量确实在模型完成前到达；无 JSON 泄漏；刷新恢复完整结果；急着分诊能给方向；不能凭空推荐医生 | 3—4 天 |
| M2 完整预约服务 | 科室/医生目录、普通挂号、我的预约、演示号源生成脚本 | Agent 和普通挂号复用同一预约服务；仅本人可查；过期/竞争/重复确认有明确结果 | 2—3 天 |
| M3 RAG 可用闭环 | 首批资料、发布/索引、searchHospitalKnowledge、可展开引用、医生资料语义匹配 | 有资料能定位来源；无资料不编；医生必须通过目录验证；实时号源始终来自 MySQL | 4—5 天 |
| M4 登录和最小管理端 | 患者/管理员登录、后端授权、资料发布/下架/重建索引、排班及记录查看 | 越权被后端拒绝；下架资料不再检索；有失败状态和审计；不建设完整医院 ERP | 3—4 天 |
| M5 稳定性和效果验证 | Redis 限流/短租约、流断恢复、Agent/RAG 场景集、错误分层 | Redis 不承载预约正确性；租约释放校验所有者；错误可追踪；产出真实测量结果 | 2—3 天 |
| M6 演示和交付 | Compose、配置模板、演示脚本、架构说明、录屏和简历依据 | 新环境能按步骤启动；Key 不入库；演示 Agent+RAG+预约闭环及失败恢复；只写有证据的指标 | 2—4 天 |

依赖顺序：M1 → M2 → M3 → M4 → M5 → M6。M3 可先用受控导入命令，M4 再补管理页面；最终交付前必须有资料发布管理。每阶段先做可操作的完整结果，再进入下一阶段，不能仅因接口存在而标记完成。

## 7. 每阶段的页面和工具交付

- 患者首页：医院服务入口、科室浏览、普通挂号、智能导诊、我的预约。
- 导诊页：对话即时反馈/真实流式、主动分诊、推荐科室和理由、来源、真实医生及号源、确认和结果；侧栏用患者语言显示进度。
- 普通挂号页：科室→医生→日期/号源→确认，不要求使用 AI。
- 我的预约：本人记录、时间、科室、医生和状态；取消/改期列为后续可选。
- 管理端：科室/医生/排班最小维护、知识资料生命周期、预约和调用记录；展示日志摘要，不展示模型隐藏思考。

Agent 最终工具控制在业务需要范围：searchDepartments、searchDoctors、findAvailableSlots、searchHospitalKnowledge、queryMyAppointments、getAppointmentRules。核验和创建由后端确认流程直接调用，不为凑工具数拆分已有查询。

## 8. 如何判断项目真正完成

### 患者体验

覆盖咳嗽、头痛、腹部不适、说不清症状、直接指定科室、着急就诊、修改偏好、无号、服务繁忙。用户发送后立即可见；建议与下一步可读；确认前不产生预约；已预约后可查。

### Agent 与业务正确性

自动验证工具白名单、非法参数、最大步骤、本人权限、方案版本/过期、幂等、竞争占号、写后核验。协议失败和上游失败分别记录；流中断不自动重放确认命令。模型相关体验用少量真实调用核实，稳定业务边界用可控模型测试。

### RAG 效果

建立约 30—50 条固定演示问题，包含同义表达、跨科室易混问题、无依据、失效资料和恶意文档指令。这些由开发维护，用户无需负责整理。先记录关键词基线，再记录向量方案结果；报告 TopK 命中、引用正确性、回答依据一致性、拒答情况和耗时。数值是实测结果，不提前编写“准确率95%”。关键门槛：不引用未返回片段、不返回下架资料、不把其他医生专长移植给当前医生。

### 可复现与展示

记录模型/Embedding/切块/索引版本和演示数据版本；少量合成资料可重建索引；演示脚本同时展示成功、无号替代、资料无依据和服务失败。源码、测试、文档三者一致后才更新完成状态。根 README 仍按用户要求暂不修改。

## 9. 首个交付版明确不做

真实 HIS/医保/支付、医生诊疗工作台、处方和用药、完整电子病历、多 Agent、微服务拆分、消息队列、Kubernetes、长期健康记忆、复杂推荐排名、大规模 OCR。取消/改期、多种检索融合和 rerank 在核心交付后按时间选择，不能阻塞简历展示版。

## 11. 执行和变更约定

下一项固定为 M1：完成已批准的流式与结构化分诊，并验证完整体验。后续会话按本表推进，报告对应阶段、完成项、遗留项和证据；“下一步”只指向阶段内任务，不替代总计划。新增大规模架构、数据库或接口变更先解释影响并确认；常规修复按已授权范围推进。

### 本次会话进展（M1）

- 已新增 `POST /api/v1/tasks/{taskId}/messages/stream`，先回传处理事件，再发送患者可读回复增量和最终业务结果。

- Java 编译、Vue 类型检查/构建、Maven 全量测试已通过；尚未把运行中的服务和浏览器端到端验收标记为完成。
- 该流式端点只负责展示回复，预约确认仍由原确认接口完成，不能通过 SSE 直接创建预约。
