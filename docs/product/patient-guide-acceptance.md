# 患者导诊与预约修复记录

验收日期：2026-10-15。环境：本地 DeepSeek、MySQL 8.0.34、Vue 患者端。均使用合成场景和模拟医院数据。

本轮用户反馈：详细描述症状后可以继续导诊，但部分科室没有演示医生/排班；着急用户会被连续追问；需要一个“发起智能分诊”入口；发送消息时用户内容延迟显示；希望明确看到科室、医生和推荐原因。

暂停检查点：上一会话暂停时，最新修改尚未经过真实模型复测。恢复后发现模型除了追问医生，也可能在已明确科室和“最近时间”的请求下重新询问症状；现已将这类偏离一并纳入校验，补充回归并部署到本地后端。完整真实模型冒烟与两次最近号源重复测试均通过。本轮早期请求曾收到 DeepSeek `service_unavailable_error`（503，服务繁忙）；稍后服务恢复，成功完成复测。该上游故障与 Agent 的追问判定是两个独立问题。

## 问题与原因

- 首页导诊按钮原来自动发送“先了解我的科室和日期需求”，对话空状态也要求患者先知道科室。
- 旧模型提示词要求具体科室、标准日期和英文时段，却没有给出当前日期；因此患者的口语时间被反复追问，回复还暴露了工具参数。
- 无匹配号源时没有稳定的备选查询策略，患者需要自己不断换条件。
- 工具调用和状态迁移事件直接组成执行记录，混入重复状态与内部术语。
- 旧适配器拒绝多个工具请求、严格解析 JSON，任何异常都会统一显示“模型决策失败”，并将任务设为不可继续的失败终态。回归测试已复现多工具请求和非 JSON 输出这两种失败路径；截图那一次的原始异常没有可追溯日志，不能断言其根因就是其中一种，也没有证据认定是 API Key 问题。
- 生成方案后输入框和后端消息入口都被关闭，无法响应患者“改成下午”的正常调整。
- 旧演示数据只有心内、呼吸、皮肤和全科，头痛建议神经内科、腹痛建议消化内科时没有对应科室和号源，导致分诊方向正确但无法继续预约。

## 实现选择

| 方案 | 原理与优点 | 局限与适用范围 |
|---|---|---|
| 只调整提示词 | 让模型自主理解、追问、查号，修改快 | 无法保证输出协议、日期或备选搜索始终正确；适合早期原型 |
| 全部使用固定规则 | 用确定性状态和关键词驱动对话，行为可预测 | 复杂表达覆盖有限，容易退化成僵硬表单；用于离线演示 |
| 模型理解 + 后端校验和查询兜底 | 模型负责自然交流；代码负责日期规范化、真实号源、备选查询和确认门禁 | 需同时验证对话与业务边界；本项目采用此方案 |

## 已实现行为

1. 空白导诊入口邀请患者描述哪里不舒服、持续多久；不再代发技术性预约消息。患者也可以直接指定科室。
2. 对常见症状给出谨慎的科室方向建议，患者接受后再查号。此功能用于导诊，不作诊断。
3. 为模型提供当前北京时间。工具边界额外支持数字月日、带年份的中文日期、今天、明天、后天和中文时段；更复杂的表达由模型理解，未宣称覆盖所有口语日期。
4. 查号只返回未来、开放、可用的号源，范围为未来 90 天。精确条件无号时保留科室和医生条件，先放宽日期，再放宽时段，标记 `exactMatch=false` 并说明替代原因。患者仍须点击确认才写入预约。
5. 预约方案必须引用本轮工具实际返回的号源；患者身份、预约日期、医生、科室和时间以后台查询记录为准。
6. 多个合法只读调用由顺序 Runtime 先处理一个，再由模型根据结果继续决策。协议格式错误最多纠正一次；网络/服务异常保留可重试状态。日志只记录任务编号、异常类别与安全原因码，不输出密钥、原始模型输出或完整对话。
7. 待确认时可继续调整需求：旧方案先标记失效，新方案增加版本；旧方案确认被拒绝。已经提交的预约不通过此路径改期。
8. 页面用中文服务文案展示进度，区分“你”“导诊助手”“系统”。咨询结束与预约成功分别显示，不能仅因任务结束就声称已预约。
9. V4 追加 140 条排班、280 个号源，本地覆盖 10 月 15—28 日。原有 6 条预约保留；页面验收确认后新增 1 条测试预约。迁移只执行一次，不会每天自动补齐未来 14 天的数据。
10. V5 追加神经内科、消化内科及各一位合成医生，未来 14 天提供上午和下午号源；当前演示库已迁移到版本 5。
11. 患者端新增“发起智能分诊”按钮。按钮使用自然语言请求当前信息下的就诊方向，不强制完整问诊；模型仍可补问影响安全判断的关键问题。发送中的患者消息会先显示在对话区，避免等待模型返回后才出现。

## 验证结果

- 本轮 Maven 全套 51 项测试通过，无失败或跳过，包含 18 项隔离 MySQL 集成测试；V5 迁移和新增头痛分诊回归均通过。
- Vue TypeScript 检查与生产构建通过。
- 真实模型 HTTP 验收通过：咳嗽后建议呼吸内科；接受建议并说“10月15号上午”生成正确方案；晚上无号时推荐同科室替代时间；“最近时间”查询最早号源，无须指定日期和时段。
- 修复后的真实模型 HTTP 冒烟再次通过：症状导诊、中文日期、无号时替代时间和最近号源均进入预期流程；另重复两次“帮我最近时间预约一个呼吸内科的号”，均直接生成待确认方案，没有追问症状、医生、日期或时段。
- 真实模型验证“我头疼”后会询问持续时间和伴随症状；点击“发起智能分诊”对应的自然语言请求后立即建议神经内科并说明原因，只补问一个与安全判断有关的关键问题。
- 浏览器实际完成：首页进入 → 描述咳嗽 → 口语日期 → 上午方案 → 调整为下午 → 确认 → 后端创建并核验。确认前预约数仍为 6，确认后为 7。
- 异常可重试、未确认不写入、旧方案失效、拒绝旧版本确认、预约幂等与竞争占号由自动化测试验证。没有为了制造故障主动中断用户的网络或模型服务。

手动复测可执行 `scripts/smoke-patient-flow.ps1`；它调用当前配置的真实模型，可能产生 API 用量，会生成演示任务与待确认方案，但不创建预约。DeepSeek 偶发 503 时可稍后重试；不要把上游服务繁忙误判成 Agent 业务决策错误。

## 下一步推荐

请用户刷新患者端并新建需求，优先验收症状导诊、着急时点击“发起智能分诊”、头痛/腹痛科室有号、发送消息即时显示、自然时间、备选推荐、调整方案和服务记录可读性。旧对话保留，旧回复不会自动改写，旧失败任务需要新建需求。

仍待确认的较大改动：真正的模型逐字流式输出，以及结构化“推荐科室/推荐医生/推荐原因”卡片。当前 SSE 仍是已持久化事件回放，当前推荐方案卡只在查到号源并生成预约方案后展示；分诊阶段的科室和原因仍在助手文本中。两项改动都需要扩展 Agent 返回协议、SSE 事件类型、前端状态和持久化字段，见本轮会话说明。
