# FreeMedi-Agent 产品核查与文档整理建议

> 核查日期：2026-11-17。
> 范围：当前工作区源码、项目文档及本地开发记录的静态核对；没有启动服务、调用模型或重跑业务测试。
> 本文第 1—6 节是首次接手检查的快照，其中的路径和去留建议对应整理前状态；归档更新见第 7 节，之后确认首版范围见第 8 节。本文不是第二份交付路线图，当前入口见[首版交付计划](delivery-roadmap-v1.md)。
> 两轮均只处理文档，没有修改业务代码、接口或数据库。核查时已有的 3 个修改文件、3 个未跟踪 Java 文件保持原样；本轮归档使用移动与快照留档，没有删除历史内容。

## 1. 本次用户明确提出的要求

- 希望建设能办理就诊服务的 Agent 项目，不接受最终只有首页 AI 问答聊天这一种主要功能形态。
- 不能把“增强 Agent”简单理解为回复更像人、增加更多患者说法或不断打磨问答。
- 判断项目问题要核对当前实现，说明问题是否实际存在，不能只提出抽象风险。
- 希望明确哪些文档仍然有用、哪些已经过时，减少多个文档同时指导开发的混乱。

这些要求是本轮记录的产品约束。上一轮助手提出的“智能就诊安排工作区”、多方案比较、表单与对话共同驱动同一任务，是候选改进方式，**尚不能视为用户已批准的具体改版或接口设计**。

## 2. 当前实现是否已经退化成聊天工具

结论：**没有完全退化，但智能导诊路径明显以聊天为主，任务操作能力不足。**

### 已有的有效基础

| 核查项 | 源码依据 | 判断 |
|---|---|---|
| 首页是否只有聊天入口 | `web/src/views/HomeView.vue` 的 `beginGuide` 与 `beginBooking`；`web/src/router.ts` | 否。首页科室入口进入普通挂号，四条患者路由存在 |
| 普通挂号能否独立办理 | `web/src/views/BookingView.vue`、`api/PortalAppointmentController.java` | 有科室/医生/日期/号源选择及提交路径，不必经过聊天 |
| 是否有真实业务结果 | `web/src/views/AppointmentsView.vue`、`appointment/AppointmentQueryService.java` | 有本人预约列表及详情，不仅是对话中的成功文字 |
| 模型是否只能沿固定顺序回答 | `agent/AgentRuntimeService.java` 的决策循环 | 可以追问、调用只读工具、读取结果、提方案或结束；不能据此宣称已覆盖所有复杂需求 |
| 模型能否绕过用户直接创建预约 | `AgentRuntimeService.confirmPlan`、`appointment/AppointmentWriteService.java` | 写入有独立确认、方案校验、事务与幂等保护；这些能力应保留 |

表中 Java 路径均相对于 `src/main/java/com/mediflow/agent/`。源码存在只能证明实现路径存在，本轮没有证明运行中的服务可用。

## 3. 已确认的问题与影响

### F1：智能导诊只呈现一个候选方案

- **事实**：`AgentView.vue` 的方案区显示固定文案“1 个方案”，围绕一个 `plan` / `slot` 渲染；`TaskSnapshot` 对外提供一个 `activePlan`。号源工具可以返回多条记录，但界面没有供用户比较、选择这些候选的列表。
- **影响**：用户难以直接比较医生、日期和偏好取舍，往往只能继续打字要求助手更换。
- **建议**：评估候选展示与明确选择机制。不能只把“1”改为动态数字；要先确定候选数据、有效期、选择和确认之间的关系。
- **状态**：已核实的交互缺口；具体方案及协议调整待评审。

### F2：需求摘要可读但不可直接编辑，结构化条件也未完整维护

- **事实**：`AgentView.vue` 的 `summaryFacts` 只读展示四类条件，没有编辑控件；`AgentTaskController` 的消息请求只接收 `message`，没有修改条件或选择候选命令。当前 Runtime 没有将这四类预约条件持续更新到 facts 的路径，主要通过历史对话与工具结果维持上下文。
- **影响**：旧布局文档所说的“修改科室、日期、时段和医生偏好”尚未成为可直接操作的能力。普通挂号中的结构化筛选也没有与同一 Agent 任务贯通。
- **建议**：先明确任务所需的最小结构化条件和变更语义，再评估表单与对话如何更新同一任务。不必因此推翻独立普通挂号路径。
- **状态**：已核实；任务条件与接口设计待评审。

### F3：在待确认方案下提问，也会让方案失效

- **事实**：`TaskContext.beginTurn` 对 `AWAITING_CONFIRMATION` 状态的任何新消息，都先将方案置为 `INVALIDATED` 并转入查询状态；未区分“改成下午”和“要带什么材料”。
- **影响**：纯解释或资料咨询也会打断正在核对的预约方案；未来接入 RAG 后尤为明显。
- **建议**：区分只读咨询与预约条件变更；真正变更仍须让旧方案失效并重新确认。不能通过放宽确认校验解决。
- **状态**：已核实的行为；实现需先评审消息分类与状态约束。

### F4：预约完成后，预期中的后续咨询走不通

- **事实**：`AgentView.vue` 的 `canReply` 不包含 `COMPLETED`；`TaskContext.beginTurn` 也不接受终态消息。“我的预约”页没有关联本次预约继续咨询的入口。
- **影响**：“完成预约 → 继续询问准备资料”目前不是同一服务过程中的完整路径。
- **建议**：确定预约执行任务结束后，如何保留预约上下文并开展只读咨询。应先比较会话承载多个任务与独立预约咨询入口，不能直接解除已完成预约任务的状态限制。
- **状态**：已核实；会话/任务边界调整待评审。

### F5：RAG 后端已有基础，患者使用链路没有接完

- **事实**：已提交代码有导入、切块、Embedding、Qdrant 和检索能力；未提交代码增加了 `KnowledgeReadToolExecutor`、组合执行器及医生校验。但 `DeepSeekDecisionModel.specifications` 只声明 `findAvailableSlots` / `getAppointmentRules`；前端没有结构化引用展示区域。
- **影响**：不能把当前版本描述为患者已能通过 Agent 检索医院资料并查看来源。
- **建议**：按 M3 第 4—6 块完成模型工具声明、调用、引用、故障/无依据处理及端到端验收。资料中的医生介绍必须经过目录校验，号源始终从业务库查询。
- **状态**：实现未完成；不是要求重新选技术栈。

### F6：部分可恢复情形仍把整项任务结束

- **事实**：Runtime 对 `INVALID_TOOL_ARGUMENT` 保留可重试状态；其他工具失败进入 `FAILED`，确认执行失败也进入 `FAILED`。前端失败后主要引导新建需求。未提交知识工具的索引故障码不在当前可恢复列表中。
- **影响**：号源被占或资料库暂时不可用时，尚缺保留需求、继续处理的完整交互。模型异常可重试，并不意味着所有故障都可恢复。
- **建议**：按业务冲突、资料不可用、模型暂时故障、已提交但核验失败分别设计恢复。核验失败不能自动重放创建预约。
- **状态**：已核实；索引故障与 Runtime 的组合路径为静态推断，尚未执行该场景。

### F7：知识资料与当前软件能力有不一致

- **事实**：`knowledge/appointment-rules.md` 描述取消、改约、爽约和同时间段预约限制；取消/改约接口与爽约管理尚未实现。该资料说“就诊开始前取消”，当前规则工具却返回 `cancelBeforeHours = 24`。
- **影响**：接入 RAG 后，助手可能把资料中的制度说成软件已经支持的操作，或给出互相矛盾的规则。
- **建议**：发布前核对合成政策与软件可办理能力，区分信息说明和可执行动作；不能因资料可检索就宣称功能已实现。
- **状态**：已核实的资料一致性问题；本轮没有改动知识正文，以免未确认的政策修改影响后续导入与版本。

### 本次纠正的旧判断

- “首页所有入口都进入聊天”：当前不成立，科室入口已进入普通挂号。
- “所有 facts 都会平铺到页面”：当前不成立，`summaryFacts` 已按 `factLabels` 白名单过滤。旧 M3 提醒需要更新；引用区域仍然缺失。
- “把回复写得更自然就能增强 Agent”：不足以解决上述任务操作与恢复问题。

## 4. 后续评审的完成标准与边界

这是用于收敛设计的建议，不是本轮直接授权改造业务代码：

1. 患者能看见真实候选、明确选择，并知道当前要确认的对象；不靠阅读长回复记住所有时间。
2. 修改预约需求与咨询说明有明确区别；修改后旧方案不能继续提交。
3. 无号、占号失败、资料服务不可用时，能解释原因，并在适当情况下保留需求继续办理。
4. 预约完成后的相关咨询能关联实际预约，同时维持写入确认边界。
5. 解释医生、服务规则和准备资料时，可定位来源；实时号源和执行结果由业务系统提供。
6. 首页、普通挂号、我的预约继续承担独立业务职责，不为扩大项目而增加与主线无关的后台模块。

推进建议：先确认上述缺口的优先级及最小交互方案，再纳入原 M1—M6 计划；不把重做全部前端、多 Agent 或新增中间件作为前置条件。大规模接口、任务模型或数据库修改仍需先说明影响并确认。

## 6. 推荐的文档治理方式

| 方式 | 优点 | 代价与适用性 |
|---|---|---|
| 直接删除旧文档 | 文件最少 | 容易丢验收证据、决策理由及引用目标，当前不推荐 |
| 全部保留且平级引用 | 无需整理 | 已出现多份“当前/下一步”冲突，不推荐继续 |
| 保留职责明确的主文档，旧计划/验收分层归档 | 可追溯且减少误读 | 需要先核对独有约束和引用；推荐 |

推荐结构：文档索引负责导航；总计划负责排期与最终范围；架构/数据库文档负责稳定约束；M3 负责当前阶段实现；历史方案和验收只提供对应日期的依据；`knowledge/` 单独作为业务资料管理。

首次核查只修入口与状态标识，没有执行移动或删除。用户随后授权先整理文档、再确定功能范围，实际执行见下节。
