## 3. 接口对抗验证（50 项，含边界、坏输入、越权、并发）

脚本：`target/api_adversarial.py`（本地工具，不纳入版本管理）。

**只读接口 22 项**

- `limit` 边界：`0` 与 `51` 返回 400，`50` 返回 200
- `period` 同时接受存储代码（`MORNING`）与口语（`上午`）；无法识别的值返回 400 并给出可选范围
- 日期无法解析（`abc`、`2026/10/20`）、月日非法（`2026-13-45`）一律返回 400，**没有出现 500**
- 不存在的科室返回 200 与空列表；超出 90 天搜索视野返回 200 与空列表
- 方法不允许返回 405，未知路径返回 404

**演示身份 5 项**：非法、`0`、负数返回 400；不存在的用户返回 403；不携带头时使用默认演示患者。

**写入接口 20 项**

- 参数校验：缺 `slotId`、缺幂等键、`slotId` 为 `0` 或负数、幂等键超过列宽 64、空 JSON、非法 JSON、无 body，全部返回 400
- 业务拒绝一律返回 **HTTP 200 + 业务码**，共 6 种：`SLOT_NOT_FOUND`、`SLOT_UNAVAILABLE`、`IDEMPOTENCY_CONFLICT`、`PLAN_NOT_FOUND`、`PLAN_NOT_CONFIRMED`、`PLAN_EXPIRED`
- 幂等键挪用给另一号源时返回 `IDEMPOTENCY_CONFLICT`，且**原号源没有被误占**
- 越权：查询他人预约号返回 404，本人返回 200；不存在的预约号返回 404
- `mine?limit=-5` 与 `limit=9999` 被夹取，不报错

**并发 3 项**：同一号源 5 个不同幂等键同时提交，**恰好 1 个成功、4 个返回 `SLOT_UNAVAILABLE`，库中只有 1 条预约**。行锁加条件更新生效，没有超卖、没有 500、没有重复创建。

## 4. 本轮修掉的问题

**审计表的三态只写了一态。** `operation_audit_log.result_status` 的列注释和 `data-model-v1.md` 都定义了 `SUCCEEDED / REJECTED / FAILED`，但实现只在成功路径末尾写审计，拒绝与失败从不落库——患者问"为什么没约上"时无据可查，M4 的失败记录查看也会缺数据。

修法与边界：

- 业务拒绝以**返回值**表达，事务正常提交，所以拒绝记录写在同一个事务里，与业务结果天然一致；记录内容包含拒绝原因（`result_code`）和被拒号源（`target_type = APPOINTMENT_SLOT`, `target_id`）
- 未预期异常会让事务回滚，那条路径改用**独立事务**尽力记录；记录失败必须不覆盖原始异常，此时应用日志是唯一记录，日志带患者、目标与原因
- **幂等重放不重复记账**：命中既有预约时不写新审计行，否则"操作次数"无法统计

验证：在运行中的服务上制造三类拒绝，审计表出现 `REJECTED / SLOT_UNAVAILABLE`、`REJECTED / SLOT_NOT_FOUND`、`REJECTED / IDEMPOTENCY_CONFLICT` 各一条且 `target_id` 指向正确号源；成功重放未新增记录；预约总数保持不变。新增两个集成用例（拒绝被记账、审计写入失败时整体回滚且不留半成品预约），并把一条**恰好断言了旧缺陷**的用例（断言审计数恒为 1）改成断言成功与被拒的分布。

## 5. 已知遗留

1. **演示数据的硬截止线是 2026-10-30。** 近期窗口为 2026-10-17 至 10-30（V4/V5 相对日期），V3 另有 12 个固定 2027-01-15 至 01-18 的号源。搜索视野是 90 天，因此 2027 年那批会陆续进入可查范围，一旦近期窗口耗尽，放宽查询会把 **2027-01-15 当作"最近可约时间"**推荐出去。演示或录屏前必须运行 `scripts/seed-demo-slots.ps1`。
2. **分诊卡片的科室 ID 已可落库，但"按此科室查号"仍未接。** 结构化卡片目前只能展示，点击跳转属于后续工作。
3. **`/slots` 对不存在的科室返回 200 与空列表**，而不是 404。对患者来说"该科室本周无号"和"该科室不存在"是同一种结果，因此保持现状；若 M4 管理端需要区分，再调整。
4. **失败审计分支没有独立用例覆盖触发条件。** 审计行与被拒原因共享 `patient_id` 与 `idempotency_key` 列，凡是这两列引发的异常都会同时让审计写入失败，因此无法通过公开接口稳定构造"失败被成功记账"的场景。现有用例覆盖的是更具价值的保证：审计写入失败时整体回滚、不留半成品预约、原始异常不被吞掉。
5. **真实登录仍未实现**，当前用 `X-Demo-User-Id` 做演示级隔离，不应宣称完整认证。
