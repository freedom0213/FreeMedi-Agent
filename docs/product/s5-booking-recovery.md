# S5 预约恢复、限时与任务追踪

S5 第一批处理号源竞争、网络重试和提交结果不确定。普通挂号和 Agent 预约共享原请求检查及写入保护。收尾补齐模型和只读工具限时、有限重试和任务追踪。

## 患者操作

- 号源被占用或失效时保留需求。Agent 作废原确认单和候选批次，按原需求重新查号后由患者选定新号源。普通挂号按原筛选刷新列表，等待重新选择。两条路径都需要再次明确确认。
- 提交失败或网络回复丢失时，页面保留同一次请求的标识和预约对象，提供「核验原预约」。恢复到已经核验成功的任务时可以直接查看原单。
- 核验找到了原预约时展示原预约编号。暂未查到时显示「暂未查到」，由患者决定继续核验或用同一个标识重试原提交。核验已获得原预约编号、仍无法核实状态时不提供重新提交操作。
- Agent 和就诊准备咨询重发同一条消息时沿用消息标识。已保存的回复直接返回，正在处理的消息等待完成，同标识换输入被拒绝。

## 数据与接口

数据库表结构不变。预约继续使用原有的患者和请求标识唯一键，明确拒绝结果通过审计表回读。写入事务按患者串行处理同一请求的记录检查，对不同患者继续按号源竞争。Agent 任务在调用预约写入前持久化请求标识与所选方案。

| 接口 | 变化 |
| --- | --- |
| `POST /api/v1/appointments/status` | 按本人、号源和原请求标识查询，返回已有预约、已记录的拒绝或 `NOT_FOUND`。 |
| `POST /api/v1/tasks/{taskId}/confirm/status` | 按本人任务、方案和原请求标识核验。已提交预约可恢复任务检查点，此入口不会调用预约创建。旧任务缺少标识时按确切方案只查原单。 |
| 既有 `POST .../confirm` | 同一标识重复时先查原结果。显式 `retry: true` 仅可在适用的未找到状态重试同一个方案。响应增加可选业务码。 |
| 既有消息和流式消息 | 可选 `clientRequestId`；同一任务内相同标识与文本重放已有轮次。 |

旧任务若缺少请求标识且按原方案查不到记录，只提示核验和查看「我的预约」，避免把旧状态当成可以重新提交的证明。

## 首批本地验收

2026-11-18 使用 Chrome、Spring Boot 和隔离 MySQL，Agent 使用确定性的本地演示模型。浏览器通过六个场景。

| 操作及故障 | 实际结果 |
| --- | --- |
| 两个患者抢同一个号，分别让 Agent 和普通挂号成为失败方 | 两种入口都保留原筛选。Agent 等待重新查候选，普通挂号按原筛选刷新。新号源等待患者重新选择和确认。 |
| Agent 写入成功后丢弃网络响应，刷新再核验 | 查询恢复同一预约编号，数据库只写了一笔。 |
| 普通挂号的首次请求在发出前中断 | 刷新后保留原提交。核验暂未查到，患者点击重试后使用同一号源及请求标识创建一次。 |
| 普通挂号写入成功后丢弃网络响应，刷新再核验 | 查到原预约编号，核验未产生新写入。 |
| Agent 消息已处理但流式响应丢失，再发同一条 | 沿用原消息标识，返回保存的回复，任务只有一条消息轮次。 |

后端回归通过 143 项，其中 60 项为 MySQL 集成测试，本批执行的测试无失败、错误或跳过。新增用例覆盖预约写入前后异常、核验不可用、同标识换号源和旧任务按原方案核验等。Vue 类型检查、Vite 生产构建和后端打包通过。日志、浏览器结果和中断页面截图在本机 `target/s5-verification/`。

首批验收覆盖 A08、A10 的预约/消息恢复场景和 A11。

## 模型与只读工具的限时

| 配置 | 默认值 | 作用 |
| --- | --- | --- |
| `MEDIFLOW_AGENT_MODEL_TIMEOUT_MS` | 15000 | 单次等待模型决策的毫秒数。DeepSeek 客户端也配置网络超时。 |
| `MEDIFLOW_AGENT_TOOL_TIMEOUT_MS` | 5000 | 单次等待只读工具的毫秒数。覆盖页面与对话查号、预约规则和资料检索。 |
| `MEDIFLOW_AGENT_REQUEST_TIMEOUT_MS` | 45000 | 同一消息或页面查号的模型和工具共用的时间预算。 |

超时会结束本次等待并尝试取消工作线程。并发使用固定容量、无排队的线程池。底层调用忽略线程中断时可能继续占用工作线程，池满时请求立即收到重试提示。数据库检查点和显式预约写入有独立的执行边界。

已识别的超时、暂时网络或数据库故障、模型限流和部分服务端故障最多自动重试一次。鉴权失败、额度拒绝和非法工具参数直接返回。模型协议校验沿用一次纠正机会，整个决策尝试共用单次限时。DeepSeek 客户端自身的自动重试已关闭。暂时失败后保留之前的预约条件和输入，患者可以再次发起请求。消息传输中断时仍使用原标识读取原回复。

预约创建由患者显式确认触发。模型和只读工具的超时重试没有预约写入权限。提交不确定仍先核验原单。流式接口保留进度事件，把已保存回复以一条文本事件发送，展示文本与最终结果一致。

## 任务追踪与收尾验收

`GET /api/v1/tasks/{taskId}/trace` 需要患者登录和本人任务归属。状态变化和动作摘要复用 `agent_state_event`，无需迁移。摘要包括轮次、步骤、尝试序号、适配器或工具名、允许公开的参数摘要、结果数量、耗时及分类错误；预约关键动作包括确认、写入、原单查回和核验。摘要省略患者原话、资料正文、模型原始响应、请求幂等键和 API 密钥。旧任务保留其已有的状态记录。运行进程突然退出后的自动接管未实现。

隔离 MySQL 回归通过 148 项，其中 61 项为 MySQL 集成用例，无失败、错误或跳过。其中一条场景让模型和工具各超时一次，确认前预约写入次数为零。随后显式确认，真实写入后模拟回复丢失，核验和重试取回同一编号，最终只有一条预约记录。另有总预算、次数上限、永久错误只调用一次、追踪身份隔离及 SSE 文本与保存回复一致的验证。

Vue 类型检查、Vite 生产构建、后端打包通过。Chrome 通过首批六个恢复场景和一条新增超时场景。用本地模拟接口延迟两次模型响应，单次限时设为 700 毫秒，约 1.7 秒返回失败并保留草稿。刷新后显式重发，模型恢复即返回真实候选。确认前预约数为零，模拟确认回包丢失后从原请求核验和重试，最终仅有原预约一笔。

真实 DeepSeek 使用应用现有配置复测两次，自然语言请求心内科近期号源后返回三个真实候选。追踪确认由 `DeepSeekDecisionModel` 生成工具决策。独立的首次 HTTP 探测返回 401，原因未核实。此次真实模型复测只覆盖一条合成查号输入，S6 继续做多输入、多轮和资料问答综合验收。

证据位于本机 `target/s5-closeout/`，包括 `mysql-suite-final.log`、`browser-final.json`、`browser-timeout.json` 和 `provider-app.json`。
