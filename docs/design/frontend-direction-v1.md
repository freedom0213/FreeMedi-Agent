# FreeMedi-Agent 前端方向 v1

> 状态：已确认产品定位和整体视觉方向；具体页面线框、文案和交互仍待细化。
>
> 项目英文名：FreeMedi-Agent

## 1. 产品定位

FreeMedi-Agent 是面向模拟医院就诊场景的智能导诊与预约编排系统。用户进入首页时，应首先感知到医院就诊服务，而不是一个通用 AI 聊天工具。

首版 Agent 负责收集预约需求、查询模拟科室/医生/号源、给出候选预约方案，并在用户确认后完成预约及结果核验。产品不提供疾病诊断、处方或个体化用药建议。

## 2. 已确认的视觉方向

采用 A+B 的组合方向：

- A（Codex-like calm）作为视觉基调：克制、清晰、内容优先、低饱和中性色和有限的强调色。
- B（Linear-like operations）作为信息组织参考：清楚表达业务状态、Agent 执行进度和关键记录。
- 不照搬 Codex/Linear 的任务编辑器或新建任务首页结构。
- 医院业务信息和就诊入口优先于聊天界面；聊天只出现在具体的智能导诊流程中。

## 3. 页面信息架构

### 3.1 首页：医院就诊服务门户

首页作为患者进入系统后的服务入口，建议包含：

- 品牌与主导航：FreeMedi-Agent、首页、智能导诊、预约挂号、我的预约。
- 就诊服务主入口：智能导诊、普通预约挂号。
- 预约需求快速入口：科室、日期/时段等结构化条件；自然语言描述作为可选补充，不将大聊天框作为首页主体。
- 服务信息：科室入口、预约规则或就诊须知，以及少量模拟号源/服务摘要。
- 明确的演示数据标识，避免让人误认为连接了真实医院系统。

首页的主要任务是帮助用户选择就诊服务并开始预约，不呈现 Agent 内部任务列表或技术执行面板。

### 3.2 智能导诊与预约

这是 Agent 的主要交互页面，围绕一次真实业务目标组织内容：

- 展示已收集的预约条件和仍需补充的信息。
- 中央区域呈现患者与 Agent 的对话；Agent 只在缺少必要信息或解释结果时追问。
- 展示候选科室、医生、日期和具体号源。
- 用户确认前明确呈现将执行的预约内容；确认操作由后端校验并执行。
- Agent 执行轨迹作为辅助信息，展示状态、只读工具调用摘要、等待确认和核验结果。

聊天是预约流程中的一种输入/反馈方式，业务方案和下一步操作始终清晰可见。

### 3.3 普通预约挂号

提供不经过 Agent 的直接预约路径，用户可按科室、医生、日期和时段查询可用号源，并确认预约。

### 3.4 我的预约

展示当前演示用户的预约记录、预约详情及状态。首版功能以已有后端 API 能力为准，不预先承诺取消或改期。

### 3.5 管理和演示能力

首版若需要管理入口，应限制在展示当前已经实现的演示数据或 Agent 运行记录，不扩张为完整医院管理后台。

## 4. 视觉与交互原则

- 以专业、清楚、可信为目标，不采用营销落地页构图。
- 使用低饱和中性色承载页面，蓝/青绿用于品牌强调或状态提示，语义颜色保持一致。
- 控制卡片、圆角、阴影和边框的数量，优先使用页面分区和明确的层级。
- 状态同时用文字和颜色表达，不依赖颜色单独传递含义。
- 主要操作清楚区分，例如“开始导诊”“查询号源”“确认预约”。
- 桌面端可并列展示需求摘要、交互内容和执行状态；窄屏按业务顺序纵向排列，避免横向滚动。
- 不使用紫色渐变、发光边框、玻璃拟态、机器人装饰或无意义的动效作为默认视觉语言。

## 6. 交付计划引用

本文只维护前端产品定位、页面层级和视觉原则，不再维护独立的临时“下一步”。前端实现、患者异常路径、结构化推荐卡片、流式消息、普通挂号、我的预约和管理端按[整体交付计划 v1](../product/delivery-roadmap-v1.md)的 M1-M6 阶段推进。

当前前端首版已实现患者首页和智能导诊页；M1 的重点是把患者消息即时显示、真正模型流式回复、主动智能分诊、结构化推荐和恢复状态做成完整体验。视觉方向仍以医院就诊门户为主，不将页面改造成通用 AI 对话编辑器。
