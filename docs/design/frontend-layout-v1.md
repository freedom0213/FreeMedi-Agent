## 1. 当前页面与职责

| 路由 | 当前实现 | 当前缺口 |
|---|---|---|
| `/` | 顶部服务导航、自然语言导诊输入、科室快捷入口和演示说明；科室来自接口，点击进入普通挂号 | 自由文本框直接进入导诊；没有独立的通用医生搜索或首页日期筛选，不能把旧设计写成现有功能 |
| `/login` | 输入预置患者账号和密码，登录后返回原业务页面 | 提供最小登录及退出流程 |
| `/guide` | 预约条件表单、流式对话、分诊查号、真实候选选择和确认单 | 完整续办仍待 S5，已完成预约可从「我的预约」继续咨询 |
| `/booking` | 科室→医生→日期/时段→号源列表→摘要与提交；用户可不使用 AI；S1 已补筛选清旧选择、查询中禁提交及过期响应丢弃 | 界面行为与完整前后端一致性仍需验证；严格查询不自动调整时间，不承诺取消和改期 |
| `/appointments` | 当前演示患者的记录、详情、预约来源 | 已接入就诊准备。取消、改期及完整个人中心尚未接入 |

普通挂号和我的预约及对应 API 已有实现，不再是“等待后端”的占位页面。预约与导诊页面在进入时核对患者会话。

S1 首批通过 6 项脚本逻辑检查，收尾再用 Chrome 实际操作登录、筛选清旧选择、确认、记录回看和 Agent 方案恢复。见[S1 验收](../product/s1-patient-session-acceptance.md)。

普通挂号的 S1 变更还包括：刷新后所选号已消失或查询失败时清除选择；仍有效的所选号按新结果更新；下单后的结果提示保留。快速切换科室或筛选时通过请求序号忽略旧响应，提交中禁止更换筛选和重新开始。以上为代码现状，具体行为证据由对应验证记录提供，不替代浏览器验收。

## 2. 当前导诊页的交互边界

- 主栏顶部可编辑科室、医生、日期和时段。科室建议卡可按已识别的科室查号。
- 候选区显示最多三个真实号源，逐条标出已允许的变化。选择后才会出现确认单。
- 纯咨询保留确认单。保存实际修改的条件会清除旧选择，患者需要重新选择并确认。
- 预约成功依赖独立确认和核验。完成后可去「我的预约」打开同一笔预约的就诊准备；完整故障续办仍待 S5。
- 进度栏将工具与状态转成患者语言；资料咨询显示查阅进度，回复可逐段展开资料标题、章节、版本与原文。
- 发送中先展示患者消息；失败后的内容保留、重试与切换会话保护不完整。
- 可按保存的任务 ID 恢复快照并回放事件，但不能据此宣称流中断、刷新后所有状态都能完整恢复。

## 3. 旧布局的实现对照

本地浏览器的实际验收及新接口见[S2 记录](../product/s2-appointment-options.md)。

| 旧意图或新讨论方向 | 状态与后续边界 |
|---|---|
| 直接编辑科室、日期、时段或医生偏好 | 已验证页面和对话共同修改同一任务 |
| 展示并选择多个候选 | 最多三条真实候选，浏览器已验证选择与实际预约一致 |
| 分诊建议直接推动查号 | 已接入可用科室建议的查号入口 |
| 等待确认时咨询资料 | 已验证就诊准备和预约规则咨询保留方案，支持可展开引用 |
| 预约完成后继续查看/咨询准备资料 | 已实现并验收。独立咨询保留原预约终态，可展开来源并返回原预约 |
| 知识引用与原文展开 | S3 首批已实现。科室和医生资料覆盖待后续验证 |

本轮不选定工作区版式；哪些条目属于核心及其完成标准以首版交付计划为准，不以增加聊天样例替代业务操作设计，也不将范围确认当作已完成实现。

## 4. 沿用的视觉与页面原则

- 保留已确认的 A+B 方向：克制的内容层级、有限蓝绿强调、清楚的业务状态。
- 首页采用医院服务门户的顶部导航，普通挂号与我的预约保留独立入口。
- 需求、将要执行的预约、执行结果与下一步操作应易于理解；进度轨迹只作辅助。
- 桌面主流程与进度侧栏、窄屏顺序重排是原设计方向；响应式与无障碍效果需实际浏览器验证，本轮没有做视觉验收。
- 不展示虚构医院规模、满意度、运营指标或模型隐藏思考。
